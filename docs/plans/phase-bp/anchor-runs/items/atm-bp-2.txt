# bp-2: plan-hardening evals and live eval runs

## Goal
Prove the skill on the cheapest tier: haiku and luna, each running it once as a background subagent and once as a teammate. Each run is against a seeded plan with planted defects, and each agent is questioned after its run.

Anchors: ANC-018, ANC-019. Requirements: `NONE`. atm-bd's role docs have numbered items and no ids; the fixes in deliverable 6 are governed by the numbered items of `docs/requirements/plan-hardening.md` (bp-1). atm-core `docs/requirements.md` §15.4 has no id; ADR-062 governs the `atm task events` that `check.sh` reads. ADR-068 is not listed: the eval runs no task hook of its own, and a teammate close goes through whatever close hook the repository already runs.

## Deliverables
1. `plugins/atm-bd-orchestration/skills/plan-hardening/evals/fixture-plan.jsonl`: a seeded plan whose ids use the prefix `eval-phase-z`, rendered from the atm-beads templates. It has four planted defects:
   - two `parallel_safe` sprints with overlapping `owned_paths`;
   - a `must_follow` sprint that consumes no named artifact;
   - a `boundary` sprint whose acceptance claims end-to-end behaviour (false closure);
   - a ledger artifact that has no consumer (ceremony).
   `plugins/atm-bd-orchestration/skills/plan-hardening/evals/planted.json` maps each defect to the plan bead that carries it.
2. `plugins/atm-bd-orchestration/skills/plan-hardening/evals/subagent.md` and `plugins/atm-bd-orchestration/skills/plan-hardening/evals/teammate.md`: the eval-runner prompts.
   - They import the fixture plan (`bd import`), run one planner-with-subagents or planner-with-teammates iteration plus the final formula against it with the agent under test, run `evals/check.sh eval-phase-z <runner>`, then burn the fixture beads (the prompt is the only place that burns them), and then ask the post-run questions.
   - Each prompt has a `## Post-run questions` section. The runner asks these of the same agent after its run closes: SendMessage for a subagent, `atm send` for a teammate. The questions are:
     - which instruction was unclear;
     - where it guessed;
     - which instruction it skipped or reinterpreted, and why;
     - what it needed but did not have;
     - what it would change.
3. `plugins/atm-bd-orchestration/skills/plan-hardening/evals/check.sh <root> <teammate|subagent>`: read-only mechanical checks that exit non-zero on any miss. Any other runner value exits 2. It never deletes or writes a bead, so it can be re-run until the prompt burns the fixture.
   - Each planted bead in `planted.json` has a `stage:plan-fix` bead with `metadata.plan_bead` equal to it.
   - Every step bead is closed with `VERDICT=PASS` or `VERDICT=FAIL` in its close reason.
   - In a teammate cell, `atm task events <step>` shows start and close.
   - In a subagent cell, there is no ATM task for the step.
   A debrief answer never counts toward a pass.
4. `plugins/atm-bd-orchestration/skills/plan-hardening/evals/README.md`: the run matrix and who runs each cell. fenix runs both haiku cells; arch-ctm runs both luna cells. It also gives the burn command the prompts run.
5. Add `test_eval_prompts_have_post_run_questions` and `test_eval_check_script_rejects_missing_fix_bead` to `plugins/atm-bd-orchestration/skills/plan-hardening/tests/test_plan_hardening.py`. The second test feeds `check.sh` recorded `bd` and `atm` outputs through `BD` and `ATM` overrides, so it needs no live database. It covers both runner branches and the refused runner value.
6. Run all four cells live. Fix each fault that a check or a debrief shows in the template, formulas, SKILL.md or references, and re-run the failed cell. Post each cell's check output and debrief answers in the PR description; they are not committed.
7. Regenerate the manifest.

## Design

## Fixture
The fixture is rendered with the atm-beads `plan-root.json.j2` and `sprint-bead.json.j2` templates. Its root is `eval-phase-z` and its sprints are `eval-z-1` to `eval-z-4`, imported into the live store under their own prefix. The runner prompt burns them after `check.sh` exits, with `bd delete --force` on each id in the fixture, so the eval never touches a real phase. `check.sh` only reads.

## check.sh
Use POSIX sh and `jq`. Read the binaries from `${BD:-bd}` and `${ATM:-atm}` so the test can stand in recorded outputs. The second argument selects the runner check: `teammate` requires `atm task events <step>` to show start and close; `subagent` requires that `atm task events <step>` finds no task. Run `bd list --parent <root> -l stage:plan-fix -n 0 --json` and match `.metadata.plan_bead` against `planted.json`. Read close reasons with `bd show <step> --json | jq -r '.[0].close_reason'`.
