# bj-2: stack bead and sprint-family pour: stack-bead.json.j2, pour metadata, pydantic model per bead kind, validate-plan

## Description

### Goal
The stack bead `<prefix>-phase-<x>.stack` exists for every phase as the ledger and the lock of its stack, poured with the phase root and required by `validate-plan`; the pour writes branch, worktree, pr_target and difficulty onto every bead of a sprint family; a pydantic model per bead kind with one validation over every bead of the phase fails the pour on any missing value. Governing text: `docs/requirements/sanity-stack.md` 1 and 2, `team-lead.md` 13, 43, atm-bd-orchestration #340. Anchors: ANC-067, ANC-078..083.

### Deliverables
1. `templates/stack-bead.json.j2` (skills/atm-beads): one bead per stack, id `<prefix>-phase-<x>.stack`, `issue_type` task, child of the phase root, labels `phase-<x>`, `stage:stack`, metadata `trunk` (the root's `integration_branch`), `stack_number` (null until the first link) and `layers` (empty list). `resources/planning.md` lists it beside `plan-root.json.j2` as rendered with the root into the plan JSONL; the lead creates it by importing that plan JSONL, never by a hand-written `bd create` (team-lead 13; this is the lead creation sanity-stack 1 and task-close-hook 20 name).
2. Layer record: each `layers` entry is `{branch, pr, head, base, linked}`; the last entry is the top; `layers` is the only record of layer order (ANC-067). `bead_schema.py` carries the `StackBead` model with `trunk`, `layers` and the entry model; the claim and the compare-and-set release are plain `bd` commands documented in `resources/orchestrating.md` ("Stack bead": `bd update <stack bead> --claim`; release `bd update <stack bead> --if-assignee "$ATM_IDENTITY" --status open --assignee ""`; the claim's 900 s lease is kept by `bd heartbeat`; an abandoned claim of this stack bead is recovered only with `bd reclaim --id <stack bead> --older-than 1800s`, then `layers` is re-derived from the hosted stack when the ledger disagrees; unscoped `bd reclaim` and event-age-as-lease-expiry are forbidden; ANC-068's claim timeout is the waiting rule, reclaim the abandoned-holder rule), used by sanity-stack (bj-3) and the lead.
3. `validate-plan`: problem 6, the stack bead is missing, is not a child of the root, or its `metadata.trunk` differs from the root's `integration_branch`; `--file` mode accepts the rendered stack bead in the file. Problem 6 applies to a phase whose root is open; a closed root is not checked; the problem line names the fix (render `stack-bead.json.j2` with the root vars and `bd import` it), so an open older phase gains the bead the same way.
4. Pour metadata (#340 item 1): at pour time every generated dev, fix, sanity and QA bead receives `branch`, `worktree`, `pr_target` and `difficulty`: `bead-groups` copies the sprint container's values onto the sprint group's dev, sanity and qa beads (ANC-078..081). `templates/qa-bead.json.j2` (the QA bead the lead creates for a finding or a quick fix) requires `branch`, `worktree` and `pr_target` from the cut layer it checks and writes all four keys, so it passes the same `stage:qa` model. Beads poured for a blocking finding (the fix group) carry the same four keys from the layer cut (#340 item 2); `assignment-gates.py` is not edited here (its readers already expect the keys on the bead).
5. One model per bead kind (#340 item 3): sprint container, dev, sanity, qa (with `checked_bead` and the round), gate, finding, fix, stack, and the sanity and qa children of a finding or fix; each names its required metadata keys; `extra="allow"` stays. `bead_schema.py validate --phase <x>` walks every bead under the phase epic (`bd list -l phase-<x> -n 0 --json`, never `--all`), picks the model from the `stage:*` label, including `stage:dev` (the root by its id, a gate by `issue_type` gate); a bead with no model is itself a problem (`<bead>: no model`), so the walk skips none (ANC-083); it exits non-zero naming each bead and missing key (#340 item 4). `bead-groups` validates the projected full graph before any persistent attach/write; `--validate` uses the same preview path. `schemas/*.schema.json` re-exported.
6. `templates/dev-fix.xml.j2` and `examples/dev-fix-vars.json` deleted; `phase-config init` no longer writes `dev_fix` and `validate-plan`/`plan_contract.py` accept a phase file without it (a sanity FAIL reopens the bead in place on the same task; nothing re-assigns a dev after a FAIL: task-close-hook.md 15). Existing phase files that still carry `dev_fix` stay valid: the key is ignored, not existence-checked. Closed sweep, in this layer: `sprint_index_common.py` (`DEFAULT_TEMPLATES` and docstring), `skills/atm-beads/tests/phase_fixtures.py`, `resources/planning.md` and `resources/orchestrating.md`, `skills/atm-bd-orchestration/SKILL.md` (the template-key list, the `test_command`/`lint_command` rows, the sanity-finding routing row, the template table), the `dev-complete.md.j2` description, the dev-fix cases of `test_templates.py`, the `dev_fix` entry in the package `README.md` `[templates]` key list, and the generated manifest/registry blocks re-run by `tests/gen_manifest.py`; `CHANGELOG.md` history and `config/legacy-owned.json` stay.
7. Tests: `bead_schema.py` model per kind with fixtures mirroring live ids (`atm-bi-7`, `atm-bi-7.group-sanity`, `atm-phase-bi.15-sanity`, `atm-phase-bi.18-qa`, a stack bead), the validate walk, `validate-plan` problem 6 and `--file` with the stack bead, `bead-groups` writing the four keys onto dev, sanity and qa beads and failing the pour on a model error.

### Pour Producers and First-Layer Transition
The producers in scope are `formulas/sprint-group.formula.toml.j2` and `formulas/finding-group.formula.toml.j2`. Generated dev/fix/sanity/QA records receive branch, worktree, pr_target and difficulty, with fix metadata taken from the recorded layer cut. Before any persistent write, validate the exact rendered prospective records together with every current phase bead. Missing metadata on an existing or prospective bead causes zero mutating calls and leaves the database unchanged; `--validate` performs the same preflight. Tests use actual sc-compose-generated records and injected failures. The stage model registry includes `stage:dev`.
