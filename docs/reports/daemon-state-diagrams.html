Daemon State Machines

These panels visualize daemon-owned runtime lifecycle and startup sequencing so same-host bootstrap, fail-closed startup dependencies, and shutdown transitions stay auditable.

CLI Bootstrap State Machine

Same-host caller bootstrap before a daemon request is sent.

Open panel

SSOT: docs/atm-daemon/cli-bootstrap-state-machine.mmd

CliComposition::bootstrap resolves the account-scoped endpoint and constructs a Tokio HTTP client. The managed daemon lifecycle is separate; bootstrap does not launch a daemon.

Notes

  • endpoint resolution and client construction are code-owned
  • a configured client does not prove daemon availability

Recovery And Visibility

Recovery Rules

  • If endpoint resolution or client construction fails, return the typed error.
  • A later request reports connection failures through the client transport.

Terminal Error Classes

  • BootstrapFailed is a caller-facing typed error.
  • ClientConfigured allows the command to issue a request.

Reachable Daemon Request Outcome State Machine

Command and doctor outcomes after bootstrap has already reached a live daemon.

Open panel

SSOT: docs/atm-daemon/reachable-daemon-request-outcome-state-machine.mmd

This machine models the current post-bootstrap split on `integrate/phase-Z`: doctor compares config and ATM roster when it can run, send requires an ATM roster member before harness resolution, and copied preexisting SQLite state may still fail schema initialization. These are reachable-daemon outcomes, not bootstrap outcomes.

Notes

  • daemon already reachable
  • state splits are command-visible
  • doctor visibility is explicit at each terminal

Recovery And Visibility

Recovery Rules

  • If a reachable-daemon command can identify the fix, return a typed caller error with recovery text.
  • If the issue is config or roster drift, doctor should report the mismatch and remediation.
  • If SQLite state cannot initialize, caller gets a typed SQLite error and doctor does not return a report.

Terminal Error Classes

  • DoctorHealthy and DoctorWarning are doctor report terminals.
  • SetupGuidanceError is a caller-facing roster/setup error that doctor should also explain.
  • SqliteStateError is a caller-facing SQLite/runtime error and doctor does not return a report.

Daemon Runtime Lifecycle State Machine

Legal daemon runtime ownership transitions after bootstrap reaches a live daemon.

Open panel

SSOT: docs/atm-daemon/runtime-lifecycle-state-machine.mmd

This machine models `RuntimeComposition::start()`, `RuntimeLifecycle`, and the fail-closed startup path in daemon composition. Every edge is a real event or guard in code, and every failure terminal is observable through a typed caller error from the active command.

Notes

  • explicit RuntimeLifecycle states only
  • startup failure rolls back to stopped
  • no direct Running to Stopped success path

Recovery And Visibility

Recovery Rules

  • If startup fails before Running, the active caller gets a typed runtime/startup error and doctor does not return a report.
  • If the daemon reaches Running, later command-specific or doctor-specific state machines own the next visible outcome.

Terminal Error Classes

  • StartupFailed is a caller-facing startup dependency error with rollback to Stopped.
  • Running is the success state that permits request serving.
  • StoppedAfterShutdown is the normal shutdown terminal.
